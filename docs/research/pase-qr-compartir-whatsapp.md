# Generar el Pase QR y compartirlo por WhatsApp desde la web

Investigación para el ticket [#5](https://github.com/Axus00/visit-pass/issues/5) (mapa [#1](https://github.com/Axus00/visit-pass/issues/1)). Fecha: 2026-09-26.

**Pregunta.** ¿Cuál es la mejor forma, desde la web app React (Vite + React 19 + TanStack Router), de generar el Pase de una Autorización y que el Residente lo comparta con el Visitante por WhatsApp?

**Respuesta corta.** Compartir un **enlace público al Pase** (`https://<app>/p/<token>`) como camino principal, con el QR renderizado dentro de esa página y también dentro de la app del Residente. Compartir la **imagen PNG** queda como acción secundaria ("Guardar imagen") para el caso sin datos. El QR codifica la misma URL del Pase, así que el Portero lee el token del QR y el Visitante puede abrir la página con la cámara. Librería: `qrcode.react` (SVG en pantalla, Canvas para exportar), nivel de corrección **M**. Detalle y fuentes abajo.

Observaciones:

- `qrcode` es la referencia en el ecosistema y la única de las cuatro con salida a Data URL PNG de una llamada (`QRCode.toDataURL(text, { errorCorrectionLevel, width, margin })`). Su README documenta el bundle de navegador y las tablas de capacidad ([README, "Error correction level" y "QR Code capacity"](https://github.com/soldair/node-qrcode#error-correction-level)). Requiere `@types/qrcode` y un `useEffect` con `ref` para pintar el canvas; no es un componente React.
- `qrcode.react` es el componente React más usado (3 veces las descargas de `react-qr-code`), no tiene dependencias, declara React 19 como peer y expone las dos superficies que necesitamos: `QRCodeSVG` para la pantalla (escala nítida en cualquier densidad) y `QRCodeCanvas` para exportar a PNG con `canvas.toBlob()`. `marginSize` genera la zona de silencio que la especificación pide (4 módulos) sin CSS extra ([README, "Available Props"](https://github.com/zpao/qrcode.react#available-props)).
- `react-qr-code` renderiza solo SVG; para obtener un PNG habría que serializar el SVG, dibujarlo en un canvas y luego `toBlob()`, que es más código que el que ahorra. Su ventaja (React Native) no aplica.
- `qr-code-styling` pesa 515 KB desempaquetado, es imperativo (no un componente) y su valor está en la estética (puntos redondeados, logo). Para un Pase que un Portero escanea en portería con luz variable y a través de una pantalla con reflejos, la ornamentación solo resta margen de lectura. No recomendada.

### Nivel de corrección de errores

Los cuatro niveles del estándar y su capacidad de recuperación, según DENSO WAVE ([qrcode.com, "Error correction feature"](https://www.qrcode.com/en/about/error_correction.html)): L 7 %, M 15 %, Q 25 %, H 30 %. M es "el más usado"; Q/H se recomiendan para entornos industriales donde el símbolo se ensucia; subir el nivel agranda el símbolo.

El README de `qrcode` añade la regla práctica: si el QR se muestra en un monitor (nuestro caso: pantalla del teléfono del Visitante), es seguro usar L o M ([README](https://github.com/soldair/node-qrcode#error-correction-level)).

**Recomendación: M.** Justificación: el Pase se muestra desde pantalla (no se degrada físicamente), pero WhatsApp recomprime las imágenes que se envían como foto y la pantalla puede tener brillo bajo o reflejos; M da margen sin engordar el símbolo. Con una URL de unos 50 bytes (`https://<dominio-corto>/p/` + token de 22 caracteres) el resultado es versión 3 o 4 (29×29 o 33×33 módulos) en modo byte, lo que a 256 px sigue siendo un módulo de ~7 px, cómodo para cualquier cámara. Con H el mismo contenido sube a versión 5 o 6 sin beneficio real. No usar L: es el valor por defecto de `qrcode.react` y `react-qr-code`, hay que fijarlo explícitamente.

Otras reglas del QR que afectan al diseño:

- Zona de silencio de 4 módulos (`marginSize={4}`) y fondo blanco sólido detrás del QR, incluso en modo oscuro.
- Tamaño en pantalla: mínimo 200 px CSS de lado, ideal ocupar el ancho del teléfono; para el PNG exportado, 512 px o 1024 px de lado (canvas con `size={512}`), suficiente para que sobreviva la recompresión de WhatsApp.
- Mantener el contenido corto: usar un dominio corto y un token en base64url (sin `=`) o base32; no meter nombre, fecha ni Apartamento en el QR, esos datos los resuelve el Portero contra el sistema (el Pase "codifica un identificador opaco", `CONTEXT.md`).

## 2. Web Share API: compartir una imagen desde la web

### Requisitos

Según MDN y la especificación W3C ([MDN `navigator.share`](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share), [W3C Web Share](https://w3c.github.io/web-share/)):

- Solo en **contexto seguro** (HTTPS) y solo con **activación transitoria** (dentro del manejador de un clic/tap; no en `onload`, no tras un `await` largo). Sin activación rechaza con `NotAllowedError`.
- Política de permisos `web-share` (por defecto `'self'`; si algún día el Pase se embebe en un iframe hay que declararla).
- `files` es un `File[]`; los tipos de imagen habituales (`image/png`, `image/jpeg`, `image/webp`, `image/svg+xml`) están en la lista de MDN de tipos que las implementaciones suelen aceptar. Hay que comprobar `navigator.canShare({ files })` **antes** de llamar a `share()`, porque un navegador puede soportar `share` de texto/URL y no de archivos ([MDN `canShare`](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/canShare)).
- El navegador puede rechazar un "hostile share" (por tamaño o tipo) con `NotAllowedError`, y la cancelación del usuario llega como `AbortError`: no es un fallo que mostrar.
- Privacidad: la API no permite saber qué app eligió el usuario ni si existe WhatsApp instalado.

El PNG se produce en cliente con `HTMLCanvasElement.toBlob()` (tipo por defecto `image/png`, disponible en todos los navegadores desde 2020, [MDN](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob)) y `new File([blob], "pase.png", { type: "image/png" })`. Ojo con la activación transitoria: el `toBlob` es asíncrono; en la práctica funciona porque resuelve en milisegundos, pero conviene preparar el blob al abrir la pantalla del Pase y no dentro del clic.

### Matriz de soporte

#### PWA instalada

- **Android (Chrome / Samsung Internet)**: una PWA instalada corre en el mismo motor con la misma hoja de compartir; `share` y `files` funcionan igual que en pestaña. web.dev recuerda que la API es especialmente valiosa en `display: standalone`, donde no hay barra del navegador con botón de compartir ([web.dev, "Integrate with the OS sharing UI"](https://web.dev/articles/web-share)).
- **iOS (web app añadida a la pantalla de inicio)**: WebKit expone `navigator.share` también en modo standalone; el mismo artículo de Jeremy Keith lo recomienda justamente para PWAs sin chrome del navegador. En la UE, desde iOS 17.4 las web apps de pantalla de inicio se abren en Safari normal (según web.dev/learn/pwa), lo que no quita soporte. No encontré en la lista de bugs de PWA ([PWA-POLICE/pwa-bugs](https://github.com/PWA-POLICE/pwa-bugs)) ningún fallo abierto específico de `share` en standalone. **Riesgo residual**: WebKit no publica una nota de versión sobre `files` (los posts de Safari 14 y 14.1 no lo mencionan; el de 14.1 dice que "una versión anterior de esta entrada describía cambios en Web Share API que no están habilitados por defecto"), así que la única fuente es BCD. Hay que probar en un iPhone real antes de dar por buena la ruta de imagen en iOS.

**Conclusión de la matriz**: entre los navegadores móviles que importan (Chrome/Samsung en Android, Safari en iOS) compartir un PNG por Web Share funciona desde 2020; el hueco es Firefox Android y cualquier WebView. Compartir **texto + URL** tiene una base algo más amplia y en Firefox Android también existe. En ambos casos se necesita un fallback que no dependa de Web Share.

## 3. `wa.me` (click to chat) como alternativa

Documentación oficial: [WhatsApp Help Center, "How to use click to chat"](https://faq.whatsapp.com/5913398998672934) (la página se renderiza con JavaScript; leída a través de un lector de texto).

- Formato: `https://wa.me/<número>` con el número en formato internacional sin ceros iniciales, paréntesis ni guiones (`https://wa.me/573001234567`, no `+57 (300) 123-4567`).
- Texto prellenado: `https://wa.me/<número>?text=<texto url-encoded>`.
- **Sin destinatario**: `https://wa.me/?text=<texto url-encoded>` abre WhatsApp mostrando la lista de contactos para elegir a quién enviarlo. Es la variante útil para nosotros: el Residente no siempre tiene el número del Visitante escrito en la Autorización y así nunca pedimos ni guardamos el teléfono del Visitante.
- La documentación **no ofrece ninguna forma de adjuntar imágenes ni archivos**; solo texto. Enviar una imagen desde un sistema propio requiere la Cloud API de WhatsApp Business, con un número de empresa, opt-in del usuario y una ventana de servicio de 24 h abierta por un mensaje del usuario ([Meta, "Send messages"](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/send-messages)), lo que descarta esa vía para un Residente que comparte un Pase.
- Funciona en todos los navegadores y sistemas (es una URL normal). En móvil con WhatsApp instalado abre la app; sin WhatsApp cae a una página de WhatsApp Web. No hay evento de éxito ni de cancelación: no sabemos si el Residente llegó a enviar.
- Cuando el texto contiene una URL, WhatsApp genera una vista previa del enlace; la página del Pase debería servir `og:title`/`og:description` neutros ("Pase de visita") sin datos personales, porque la vista previa se cachea y la ven terceros a los que se reenvíe.

`wa.me` sirve, por tanto, como **fallback universal de la variante enlace** (y como acción explícita "Enviar por WhatsApp" que muchos usuarios prefieren a la hoja de compartir genérica), pero no como fallback de la variante imagen.

### 4.2 Recomendación

**Enlace público como camino principal; imagen como complemento, no como alternativa.**

1. Al crear la Autorización, el backend genera un token por Pase y guarda la Autorización con ese token. La app del Residente muestra el QR (`QRCodeSVG`, nivel M, `marginSize={4}`) con el contenido `https://<dominio>/p/<token>`.
2. Botón principal **"Enviar por WhatsApp"**: construye el texto ("Hola {nombre}, este es tu Pase para visitar el apartamento {torre}-{número} en {Unidad residencial} el {fecha}: {url}") y llama a `navigator.share({ text, url })` si existe; si no, abre `https://wa.me/?text=<encoded>` en una pestaña nueva. Pasar la URL dentro de `text` además de en `url` para que sobreviva al "Copiar" de iOS y a `wa.me`, que solo tiene texto.
3. Botón secundario **"Guardar imagen"** (en la app del Residente y en la página pública del Pase): `QRCodeCanvas` oculto de 512 px, `toBlob` → `File`; si `navigator.canShare({ files })`, `share({ files, title })`; si no, descarga con `<a download="pase.png">`. Cubre el caso "el Visitante no tendrá datos en portería".
4. La página `/p/$token` renderiza el mismo QR, el estado (válido hoy, vence el…, cancelado, usado), instrucciones y el aviso de privacidad; no requiere sesión. No muestra el documento del Visitante ni el nombre completo del Residente: lo mínimo para que el Visitante y el Portero se entiendan.
5. El escáner del Portero acepta tanto la URL completa como el token pelado y resuelve la Autorización por el token; así el mismo QR sirve para la cámara nativa del teléfono del Visitante (abre la página) y para la app de portería.

Por qué no "solo imagen": obliga a Web Share con archivos (sin fallback digno en Firefox Android/WebView), pierde la revocación, y deja al Visitante sin contexto ni aviso de privacidad. Por qué no "solo enlace": el escenario sin datos en portería es real y barato de cubrir.

## 5. Protección del enlace público

El enlace es una **capability URL**: quien lo tenga accede al Pase. No hay cuenta del Visitante (por definición, `CONTEXT.md`), así que toda la seguridad recae en el token y en la verificación presencial del Portero.

### Token

- **Aleatorio y de un CSPRNG.** OWASP pide, para identificadores que autorizan por sí solos, al menos 64 bits de entropía generados por un CSPRNG, y advierte que cualquier parte predecible reduce la entropía efectiva ([OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)); para tokens que viajan en URL (reset de contraseña) exige CSPRNG, longitud suficiente contra fuerza bruta, vínculo a un registro concreto, expiración y rate limiting ([OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)).
- **Recomendación: 128 bits** (`crypto.getRandomValues(new Uint8Array(16))`) codificados en **base64url sin relleno (22 caracteres)** o en base32 Crockford (26 caracteres, sin ambigüedad O/0 si alguien lo dicta por teléfono). 128 bits hacen la enumeración inviable aunque no hubiera rate limiting; 64 bits sería el mínimo, no el objetivo. `crypto.randomUUID()` da 122 bits y es aceptable, pero 36 caracteres alargan el QR y la URL sin ganar nada ([MDN `randomUUID`](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID), [MDN `getRandomValues`](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues)).
- **Dónde se genera.** En la mutación que crea la Autorización, nunca en el cliente. Convex documenta que `Math.random()` en queries y mutations es un PRNG **sembrado** para mantener el determinismo, y lista Web Crypto (`crypto`, `SubtleCrypto`) entre las APIs del runtime por defecto ([Convex, "Runtimes"](https://docs.convex.dev/functions/runtimes)). La documentación no afirma explícitamente que `crypto.getRandomValues` sea no determinista dentro de una mutación: **verificar en la implementación** (generar dos tokens en dos llamadas y en dos deploys) antes de confiar; si no lo fuera, generar el token en una action y pasarlo a la mutación interna.
- **No es el `_id` del documento.** Los `Id` de Convex no están diseñados como secretos; el token vive en un campo propio con índice `by_token`.
- **Almacenamiento.** Con 128 bits aleatorios, guardar el token en claro e indexarlo es aceptable; guardar solo `sha256(token)` (defensa en profundidad contra fuga de base de datos, como pide OWASP para tokens de reset) es barato y compatible con el índice, a costa de no poder reconstruir la URL desde el dashboard. Decidir en el ADR de implementación; el resto del diseño no cambia.
- **Un token por Pase**, no por Autorización: una Autorización de tipo Evento tiene un Pase por Visitante (`CONTEXT.md`), y cada Visitante debe poder ser cancelado por separado.

### Expiración y estado

- **Ligado a la Autorización, no un TTL propio.** El Pase "vale el día completo de su fecha" (Temporal, Evento) o el rango y días de semana (Servicio). La query pública devuelve el estado calculado: `vigente`, `aún no válido`, `vencido`, `cancelado`, `usado` (Temporal tras su único Ingreso). La página lo muestra, y el escáner del Portero rechaza todo lo que no sea `vigente`.
- **Ventana de gracia de lectura.** Tras vencer o cancelarse, la página puede seguir resolviendo el token unos días para mostrar "este Pase venció el…" en lugar de un 404 opaco: menos llamadas a portería. Después, 404 genérico.
- **Un solo uso** aplica al Ingreso del Pase Temporal, no a la apertura del enlace: el Visitante lo abre varias veces (al recibirlo, camino a la portería). No invalidar el token por lecturas.
- **Rotación.** "Regenerar Pase" en la app del Residente invalida el token anterior y emite uno nuevo; es la respuesta a "lo reenvié a quien no debía".

### Superficie de fuga y mitigaciones

- URL en historial, logs y `Referer`: la página del Pase declara `<meta name="referrer" content="no-referrer">` y no enlaza a terceros (OWASP Forgot Password recomienda `noreferrer` para URLs con token).
- Vista previa de WhatsApp: `og:` neutros y `robots: noindex`.
- Enumeración: con 128 bits es impracticable; aun así, si la query pública se expone como HTTP action (`.convex.site`, pública por defecto, [Convex, "HTTP actions"](https://docs.convex.dev/functions/http-actions)) se puede añadir `@convex-dev/rate-limiter` por IP ([componente](https://www.convex.dev/components/rate-limiter)); una query Convex normal no ve la IP, así que allí la protección es la entropía. Responder siempre el mismo 404 para token inexistente y token de otra Unidad residencial.
- Datos mínimos: la página no expone documento de identidad, teléfono ni el nombre completo del Residente. El Portero ve el detalle en su app tras escanear, no en la página pública.

## 6. Riesgos

| Riesgo                                                                                                              | Impacto                                        | Mitigación                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Web Share con `files` falla en un navegador/PWA concreto (sin nota oficial de WebKit; Firefox Android sin soporte). | El botón "Guardar imagen" no abre WhatsApp.    | `canShare` antes de mostrar la acción; fallback a descarga; el camino principal (enlace) no depende de `files`. Probar en iPhone real, standalone y en Safari.                                                                |
| Visitante sin datos en portería.                                                                                    | No puede abrir la página.                      | El mensaje de WhatsApp genera preview y el Visitante suele abrirlo al recibirlo; botón "Guardar imagen" en la página; el Portero puede buscar al Visitante por nombre/documento como Registro manual con Autorización previa. |
| Reenvío del enlace a un tercero.                                                                                    | Alguien no autorizado presenta un Pase válido. | Igual que con la imagen: el Portero coteja documento con el nombre de la Autorización; Pase Temporal de un solo Ingreso; "Regenerar Pase" para revocar.                                                                       |
| WhatsApp recomprime el PNG y el QR no se lee.                                                                       | Fallo en portería con la ruta imagen.          | Exportar a 512–1024 px, nivel M, fondo blanco, margen de 4 módulos.                                                                                                                                                           |
| iOS copia `text` y no `url` al "Copiar".                                                                            | El Residente pega un texto sin enlace.         | Incluir la URL dentro de `text`.                                                                                                                                                                                              |
| `crypto.getRandomValues` resultara determinista en mutaciones de Convex.                                            | Tokens repetibles entre ejecuciones.           | Verificación explícita al implementar; si falla, generar en action.                                                                                                                                                           |
| Token en logs de CDN/analítica.                                                                                     | Fuga de Pases vigentes.                        | No enviar la ruta completa a analítica; `no-referrer`; ventana de validez corta por naturaleza (un día).                                                                                                                      |
| Nivel L por defecto en las librerías React.                                                                         | QR frágil.                                     | Fijar `level="M"` explícitamente y cubrirlo con un test de render.                                                                                                                                                            |

## 7. Decisiones que quedan para la implementación (#15)

- Confirmar la aleatoriedad de `crypto.getRandomValues` en mutaciones de Convex y elegir entre token en claro con índice o hash SHA-256.
- Dominio corto para las URLs del Pase (afecta al tamaño del QR).
- Textos del mensaje de WhatsApp y de la página pública, incluido el aviso de privacidad.
- Si la query pública del Pase se expone como query Convex o como HTTP action con rate limiting.

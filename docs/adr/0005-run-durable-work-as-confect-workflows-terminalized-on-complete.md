# Run Durable Work as Confect Workflows Terminalized on Complete

Multi-step or failure-prone work runs on `@convex-dev/workflow`. A public Confect mutation inserts a request row in its in-progress status (`generating` in `shiftReports`) and starts the workflow through a raw internal mutation; the workflow body is an Effect that calls journaled steps through `Workflows.makeConfectWorkflowRunner`, so every step keeps Confect's encoded arguments, decoded returns, and typed errors; and the component's `onComplete` handler terminalizes the row into a terminal status (`ready` or `failed` in `shiftReports`, where a failure after the file was stored stays `ready` so it remains downloadable), then calls `workflowManager.cleanup` to delete the finished workflow and its step journal, which the component never removes on its own. Cleanup runs after terminalization and its failure is only logged, because the row, not the workflow, is the durable record. Clients subscribe to the row, never to the workflow component, so progress is an ordinary reactive query.

A typed failure from a step reaches `onComplete` only as text, often wrapped in `Workflows/UnknownError` by the runner, so `Workflows.classifyWorkflowError` recovers the first tag the workflow's declared error union knows, and the row stores that tag (`failureReason`, or `canceled` for a canceled run), never finished copy; the read path derives the user-facing message from it. A step that calls a rate-limited provider passes its own `retry` policy instead of the workpool default, as the `shiftReports` email step does. The workflow definition, start, and completion handlers stay in a plain `<group>.ts` file registered with `FunctionSpec.convexInternalMutation`, because defining them inside Confect creates a self-referential codegen type cycle. `shiftReports` is the reference implementation of this shape.
